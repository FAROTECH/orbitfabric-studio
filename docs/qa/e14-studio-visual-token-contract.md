# E14 — Studio Visual Token Contract

Generated by: manual hardening slice  
Scope: OrbitFabric Studio visual semantics  
Status: draft until local QA and PR review pass

## 1. Intent

E14 defines the first semantic visual token contract for OrbitFabric Studio.

This is a foundation slice, not a restyling slice. The goal is to give future
visual harmonization PRs a stable vocabulary for common UI meanings before any
surface-specific migration starts.

## 2. Baseline

E13 documented that the stabilized Studio desktop surfaces now share a desktop
envelope contract, but still use different visual dialects for headers, cards,
badges, provenance, clickability, selected state, raw blocks, tables, lists and
Data Flow sub-surfaces.

E14 responds by creating additive semantic tokens under the `--of-visual-*`
namespace.

## 3. Non-goals

E14 must not:

- change OrbitFabric Core
- change the reference mission
- change generated mission data
- change command behavior
- change scenario execution
- change artifact generation
- change graph/data-flow semantics
- add private inference
- migrate existing surfaces
- perform a visual redesign
- alter layout, scroll, density or desktop envelope behavior
- expand mobile/tablet scope

## 5. Import position

`studioVisualSemantics.css` is imported immediately after
`desktopEnvelopePrimitives.css`.

Reason:

- desktop primitive tokens remain the lower-level layout/desktop contract
- visual semantic tokens can reference desktop primitives
- surface bridge CSS remains downstream and unchanged

## 6. Namespace contract

All new semantic visual tokens use:

```text
--of-visual-*
```

This namespace is intentionally separate from:

```text
--of-desktop-*
```

`--of-desktop-*` remains the desktop envelope/layout primitive layer.

`--of-visual-*` is the semantic visual language to be consumed by future
harmonization slices.

## 7. Semantic groups

### Surface grammar

Tokens define surface, panel, card and raised background meanings.

These are not layout primitives. They express visual meaning only.

### Border grammar

Tokens distinguish:

- soft border
- default border
- strong/accent border
- divider

### Text hierarchy

Tokens distinguish:

- primary text
- secondary text
- muted text
- faint text
- inverse text

### Accent grammar

Tokens define the shared Studio accent and muted/accent-border variants.

### Status grammar

Tokens distinguish:

- success
- warning
- danger
- info
- neutral

Each status has foreground, background and border tokens.

### Provenance and evidence grammar

Provenance and evidence receive separate token groups so future UI work can stop
overloading generic status colors for lineage, source, proof and execution state.

### Interaction grammar

Tokens define:

- actionable default state
- actionable hover state
- selected state
- focus ring
- disabled opacity

### Raw/code/output grammar

Raw and code-like blocks receive explicit visual tokens so JSON, generated
payloads, evidence snippets and output consoles can converge later.

### Shape grammar

Tokens distinguish:

- panel radius
- card radius
- control radius
- pill radius

## 8. Constraints for future PRs

Future PRs may consume these tokens only through narrow harmonization slices.

Expected sequence:

1. E15 — Hero/Header Harmonization
2. E16 — Status/Badge/Provenance Harmonization
3. E17 — Clickable/Selected/Focus Affordance Harmonization
4. E18 — Card/Panel/Table/List Harmonization
5. E19 — Data Flow Visual Integration Pass

Each slice must preserve the read-only downstream nature of Studio.

## 10. Acceptance criteria

E14 is acceptable when:

- `src/studioVisualSemantics.css` exists
- the file defines only additive `:root` semantic tokens
- all semantic token names use the `--of-visual-*` namespace
- `src/main.tsx` imports the file immediately after `desktopEnvelopePrimitives.css`
- `package.json` exposes `qa:studio-visual-token-contract`
- the QA script passes
- the build passes
- no runtime surface migration is included
- the PR remains small and reviewable
